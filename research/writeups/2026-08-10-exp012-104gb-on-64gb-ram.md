# I ran a 104 GB LLM on a 64 GB RAM + 12 GB VRAM machine. Here's the honest number.

> **TL;DR:** DeepSeek-V4-Flash-0731 (UD-IQ3_XXS, **104 GB**) runs on an
> i9-9900KF + RTX 3060 12 GB + 64 GB RAM at **1.5–1.9 tok/s**, proven
> disk-bound by OS-level telemetry: **36,000–77,000 page faults per token
> ≈ 150–300 MB read from disk for every token generated.** It works. It is
> not fast. And that's the point of the project: **measure the real cost of
> running models bigger than your hardware, honestly.**
>
> Screenshots of the console (live tok/s, page-fault demand, VRAM) and a
> short demo GIF: [`docs/screenshots/`](../docs/screenshots/) — all real
> captures from this machine.

## Why this matters

Everyone is benchmarking LLMs they *can* run. Almost nobody publishes the
number for the model they *can't* fit — the one that spills past RAM and
VRAM into the SSD. The default behavior in the community is to either
claim it's fine (it isn't) or to not talk about it.

This project exists to answer the question with real telemetry: **how much
does it actually cost to run a model larger than your machine?**

**Machine under test (consumer, fixed, unchangeable):**

| Part | Spec |
|---|---|
| CPU | Intel i9-9900KF (8C/16T) |
| GPU | NVIDIA RTX 3060 **12 GB** |
| RAM | 64 GB DDR4 |
| Disk | NVMe |
| OS | Windows 11 |

**Model:** DeepSeek-V4-Flash-0731 (284B MoE, 34B active), unsloth
UD-IQ3_XXS quant = **104 GB** across 4 GGUF shards (shard 1 is a 5 MB
metadata-only header — a legit llama.cpp split layout).

## The honest numbers

| config | cold tok/s | warm tok/s | page faults/tok | disk MB/tok |
|---|---:|---:|---:|---:|
| all-expert CPU, t8 | 1.48 | 1.76 | 68,009 | ~150–270 |
| 42-layer MoE tiering, t8 | 1.46 | **1.89** | 76,548 | ~160–300 |
| all-expert CPU, t16 | 1.71 | 1.75 | 64,935 | ~145–260 |
| auto placement (n-cpu-moe 0), t8 | 1.65 | 1.83 | 62,933 | ~150–250 |
| forced `-ngl 99` (everything to GPU) | **OOM** | — | — | — |

Notes:
- Cold = first run after boot (empty page cache); warm = second run
  (weights partially cached by the OS).
- **Config tweaks move the number only ~15%.** Because the bottleneck is
  not the CPU and not the GPU — it's the disk→RAM→CPU pipeline.
- `n-cpu-moe 0` (llama.cpp auto placement, ~7–9 GB into VRAM) runs fine.
  Forcing everything into 12 GB VRAM fails with `cudaMalloc 77,361 MiB`.

## Why it's slow: the telemetry tells you exactly

The page-fault counter (Windows `GetProcessMemoryInfo` / `PageFaultCount`)
during generation:

- **36k–77k major faults per token**
- At 4 KB per fault, that's **~150–300 MB read from disk per token**

A 284B MoE model activates ~34B parameters per token; its working set
thrashes in and out of RAM every single token because RAM can hold only
~60% of the file. The GPU and CPU are idle-ish *waiting* for the disk.
More threads? Doesn't matter. More VRAM tiering? Doesn't matter. The disk
is the wall.

This is measurable, reproducible, and — as far as we can tell — rarely
shown so plainly anywhere.

## The number nobody quotes: effective disk bandwidth

Those raw faults translate to the one number that explains everything:
**~150–300 MB read from disk per token at ~1.9 tok/s → an effective
bandwidth of ~0.3–0.6 GB/s** (mid ~0.38 GB/s, our calibrated disk-mmap
tier in EXP-025). Not the 14 GB/s NVMe sequential spec you see in the
spec sheet — page-fault reads are random-access single pages, and that is
what actually streams through the pipeline.

That calibrated number is now a first-class tier in the project's physics
model (`simulator/physics.py`), so we can predict — not guess — what
happens to any model on any machine: `tok/s = bandwidth ÷ bytes per
token`. Qwen (fits RAM) gets ~23 tok/s from RAM; K3 (15.6 GB/token,
EXP-029) gets **0.049 tok/s at a 51% hit rate** and only reaches its
1.18 tok/s compute ceiling when the buffer keeps hit rate ≥ 99%. The
~24× gap between those two K3 numbers is precisely the project's upside:
**buffer/prefetch is worth everything when the model doesn't fit; nothing
when it does** (EXP-026/027/029).

## The dead ends we closed (also honestly)

The project's research log records **29 experiments** (EXP-001…EXP-029),
including four dead ends that other projects would quietly skip:

- **Speculative decoding (MTP head, llama.cpp `draft-mtp`)** — *slower* on
  this machine (−11–18%): the draft step still runs the full 256-expert
  forward pass, and the model file with the MTP head embedded (+1.3 GB)
  stopped fitting VRAM cleanly.
- **Expert census → hot-expert tiering** — expert activation is *flat*
  across layers (no "hot" experts to promote to VRAM); placement gains
  track bytes-on-GPU, not layer position.
- **CPU lane (compute hot experts on CPU, pulsar-style)** — the CPU was
  only 39–51% busy while the DDR4 *bandwidth* was saturated. Adding work
  to a bandwidth-bound CPU doesn't help.
- **quant ladder** — the single lever that *does* move the needle is
  bytes-per-token (IQ1_M vs IQ2_M on a 10 GB MoE = 77 vs 56 tok/s). Lower
  bytes → more of the model resident → fewer faults.

The lesson: on a bandwidth-bound pipeline, **every optimization is a
bytes-per-token play**. Tricks help only where bandwidth isn't the wall.

## What would actually fix it

The physics says: to run a 104 GB model smoothly you need either

1. **RAM ≥ model size** (128 GB keeps the whole file in page cache →
   faults only on first touch), or
2. **VRAM ≥ the active working set** (experts resident on GPU),
3. plus a fast enough NVMe for whatever spills.

That's it. No software trick replaces RAM/VRAM on a bandwidth wall. The
project's [`HARDWARE_100TPS_PLAN`](../../research/HARDWARE_100TPS_PLAN.md)
lays out the cheapest path to 100+ tok/s with 2026 prices.

## The takeaway

- A **104 GB model runs on a 64 GB machine** — at ~1.5–1.9 tok/s, usable
  for batch jobs, drafts, and slow-but-real conversations.
- The cost is **measurable, not vibes**: page faults per token and disk
  MB/token are the honest numbers nobody else publishes.
- **Buy hardware with data, not hype.** Use an honest benchmark harness to
  see where YOUR bottleneck is before you spend.

**รันโมเดล 104 GB บน RAM 64 GB + การ์ด 12 GB — ตัวเลขจริงที่ไม่มีใครกล้าโชว์**

เครื่อง i9-9900KF + RTX 3060 12 GB + RAM 64 GB รัน DeepSeek-V4-Flash-0731
(104 GB) ได้จริงที่ **1.5–1.9 tok/s** — พิสูจน์ด้วย telemetry ระดับ OS ว่า
คอขวดคือดิสก์ ไม่ใช่ CPU/GPU: **36,000–77,000 page faults ต่อโทเคน =
อ่านดิสก์ 150–300 MB ต่อโทเคน**

สิ่งที่ค้นพบ:

- **ปรับ config ได้กำไรแค่ ~15%** — เพราะ bottleneck อยู่ที่ pipeline
  disk→RAM→CPU ไม่ใช่ความแรงของ CPU/GPU
- **ตัวเลขที่ไม่มีใครบอก: effective disk bandwidth ~0.38 GB/s** (150–300
  MB/โทเคน ÷ 1.9 tok/s) — ไม่ใช่ 14 GB/s ตาม spec ของ NVMe เพราะ
  page-fault read เป็น random access ตัวเลขนี้ถูก calibrate เข้า
  physics model (EXP-025): `tok/s = bandwidth ÷ bytes/โทเคน`
- **ทางตัน 4 เส้นที่เราปิดพร้อมหลักฐาน:** speculative decoding ช้าลง,
  expert census พบว่าไม่มี "hot layer", CPU lane ไม่ช่วยเพราะ RAM
  bandwidth อิ่ม, และจุดที่ได้ผลจริงคือลด bytes/token (quant)
- **ทำนายได้แล้ว (EXP-029):** K3 (15.6 GB/โทเคน) ที่ hit rate 51% =
  0.049 tok/s; ต้อง hit ≥ 99% ถึงจะถึง compute ceiling 1.18 tok/s —
  buffer มีค่าสุดเมื่อโมเดลไม่พอดี RAM (~24×) และไม่มีค่าเมื่อพอดี
- **บทเรียน: บน bandwidth-bound ทุก optimization คือเกมลด bytes ต่อ
  โทเคน** — tricks ช่วยได้เฉพาะตอน bandwidth ไม่ใช่กำแพง
